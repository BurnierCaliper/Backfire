## PRD 结论

按 **D1 统一指令 → D2 热座 → D3 在线跑团 → D4 合作单局** 开发。每期单独 PR，作者评审合并后再开始下一期。Q1–Q17 已确认，无需重新征求这些既定决策。此前 R1 文档中的“阶段 D 暂不开发”是历史范围，当前联机安排以 v1.0 为准。

没有需要重新决定产品方向才能开始 D1 的阻塞，以下边界应在实现和验收清单里明确。

| 检查项 | 证据与影响 | 开发处理 |
| --- | --- | --- |
| D1 操作清单需覆盖现有跑团入口 | PRD 4.4 和 D1 要求“所有单机入口”，详细清单主要列战斗及 Roguelike；`trpg-ui.js` 的探索、发经验、休息、购买和现有后台仍有直接规则调用 | 开工先枚举全部现有状态变更入口。按“所有单机入口”的总要求，既有跑团操作也需有指令和回归；D3 新增的联网、主持人功能仍按 D3 交付，不提前扩展功能范围 |
| 隐藏信息不能只过滤 `state` | `game.js::snapUnit` 和 `tape.pop.snap` 含坚毅数值，主持人日志也可能含数值；现有起身与战斗存活判断依赖 `shp`，删除字段后直接复用规则会误判 | 指令执行保留完整权威状态，玩家视图与可操作性结果分开。D1 接口为此保留边界；D3 对整个结果、演出、日志、重同步及私信历史做收件人过滤，客户端不能拿脱敏状态作权威规则结算 |

## D1 交付边界

D1 只完成现有操作的可序列化指令入口、单机等价性与指令日志导出；不部署联机服务。现有评分、角色/敌人数值、单机存档兼容性保持不变。后续实现按 PRD 验证固定种子的旧调用/指令结果一致、JSON 往返，以及 `npm test`、`npm run test:ui`；真实设备与网络验收留到相应联机阶段。
