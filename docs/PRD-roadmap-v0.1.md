## 1. 产品目标与用户

Backfire 是基于同一套规则的浏览器回合制游戏，包含 Roguelike、单人模式与主持人跑团工具。现有游戏可以本地打开，不需要服务端。

| 用户 | 需要解决的问题 | 本路线的价值 |
| --- | --- | --- |
| Roguelike 玩家 | 不同人数、幕次的挑战与评分是否合理；任务缺少正式内容 | 先建立可信难度依据，再补充有明确选择与反馈的内容 |
| 新玩家 | 不理解行动、射程、协助、休息和主线期限 | 通过可跳过、可回看的引导理解核心循环 |
| 跑团主持人 | 同一规则在计算器、战斗和存档中保持一致 | 共用规则修正有回归保护，后续联机保留主持人权限 |
| 开发合作者 | 现有模拟结果能否支持调参 | 固定样本、明确口径、可重跑的报告与自动检查 |

首期成功标准是「能够可靠解释并复现多人队伍的表现，为后续玩家测试提供数据」，不调整评分，也不要求自动策略必定通关。

## 4. R1 详细需求

### R1-01：让测量工具与真实游戏结算一致

1. 经济脚本遇到分岔时通过现有合法选路 API 继续；路径策略固定并写入报告。检查休息被偷袭、任务结算、幕间等状态，不能靠强改阶段绕过未知流程。
2. 将「胜利后最终评分与评价额外经验」提取到可在网页和 Node 共用的结算入口，或实现经测试证明等价的共享规则。保留当前玩家界面已经执行的算法与倍率。
3. 同一场战斗多次触发结算也只能发放一次奖励；撤退、失败、已死亡角色等边界保持现有玩家端规则。
4. 采样输出区分胜利、失败、主动撤退、回合上限超时、脚本异常。脚本异常不能被吞掉后当作正常败局；工具错误或配置错误返回非零退出码。正常输掉一局不等于脚本失败。
5. 单场测试默认不额外加等级；诊断用强化必须通过显式参数启用，并与正式基线分表展示。角色等级、武器等级、升级选择、义体与道具假设都必须记录。
6. 经济脚本仍是「假定战斗全胜、评级经验倍率固定 ×1」的经济模型，报告明确这两个假设，不能用来报告战斗胜率。其直接击杀敌人的流程不能产生虚构的速杀/无伤评级经验；真实评级奖励的成长影响由整局实战模拟验证。

验收：分岔不再触发空节点异常；S/A/B/C/D 评价、胜利/失败/撤退、重复结算有规则测试；相同战斗状态经网页调用路径和无界面路径结算后，评分、经验增量、等级与待选升级一致。

### R1-02：建立可复现的多人评估报告

**单场矩阵：**第 1–4 幕 × 普通/精英/首领 × 2/3/4 人，共 36 格。开发时每格 10 场冒烟；正式评估每格至少 100 个固定种子，另使用不重叠的每格 50 个种子验证，合计至少 5,400 场。

**整局样本：**基线集每种开局人数至少 30 局，共 90 局；另设每种人数至少 15 局、共 45 局的独立整局验证集，种子不与基线集重叠，两组预先冻结。使用固定种子与预先保存的队伍清单，两组均在每种人数中覆盖现有 10 名角色且每名至少出现 2 次；记录实际阵容，不把武器人计入玩家人数。直接从新局走完整流程，不把角色等级手动调成敌人等级。本期只有现行评分配置，不再生成/比较候选门槛；单场验证不能替代整局验证。

队伍减员后，同时记录「开局人数」和「本场存活英雄数」，整局按开局人数归组。朴素单场策略与现有较复杂整局策略分别标注，自动策略的局限不能解释为真人水平。现有 SMART 策略本身优化评分增量，且默认不使用部分武器人召唤与道具，报告必须披露这些偏向；本期不把自动策略升级成全功能玩家 AI。

| 报告 | 必须显示的内容 |
| --- | --- |
| 单场结果 | 幕次、战斗类型、队伍、实际等级、种子、策略、天气/地形、结局、回合数、原始/最终分、评价 |
| 分组汇总 | 请求样本数、成功执行数、异常数、胜/败/撤退/超时、胜率及样本量、胜率 95% 区间、得分 P25/P50/P75/P90、评价分布 |
| 整局结果 | 到达各幕的人数、各幕首领胜率、整局通关率、结束原因、阵亡、等级/武器等级、经济与补给情况 |
| 可追溯信息 | 代码提交、配置快照或校验值、Node 版本、命令、种子清单、策略版本、诊断强化参数 |

胜率口径固定：单场胜率 = 胜场 / 成功执行的样本数（包括败、撤退、超时）；异常单列且使正式报告不合格。各幕首领胜率 = 该幕首领胜场 / 实际进入该首领战的场数，同时显示各幕到达率；总通关率以全部合法开局为分母。

输出一份便于审阅的 Markdown 报告，以及 JSON/CSV 原始记录。未到达的后期幕次、无胜局的分位数显示「无样本/无法估计」，不能显示成 0 分或伪造后续关卡结果。首领种类覆盖不足时增加明确标注的定向场景，不混入随机样本。

验收：36 格都有足量可执行样本；整局基线/验证集至少 135 局全部终止于合法结果，或明确暴露未解决的阻塞；同代码、同配置、同策略重跑指定种子，核心结果一致（忽略耗时、时间戳等元数据）。正式报告不能含未说明的异常、超时或缺失数据。

### R1-03：评分保持现状，供后续玩家测试手调

用户已取消本期自动校准：不生成候选阈值、不实施分位数政策、不移动评分配置、不调整按幕增量或人数归一化。报告保留原始/最终分、分位数和既有评价分布，作为玩家测试的参考数据。

保留总分组成、招式疲劳、速杀/无伤/遭遇战奖励，以及 D/C ×1、B ×1.2、A ×1.5、S ×2 的经验倍率。所有模式的既有门槛保持一致；共享结算仅修正无界面工具漏发既有评级奖励的问题。验收以配置差异检查、原门槛边界与奖励回归为准。

### R1-04：兼容性与开发交付

- 保留本地打开 `game.html` / `index.html` 的使用方式，不增加游戏运行时网络依赖。
- 单人、多人、跑团分别做回归；对共享结算修正，验证网页端经验没有多发或少发。引入持久化字段时，必须按仓库约定升级存档版本并提供迁移；尽量不为统计报告修改玩家存档。
- 修改规则时，在 README「规则改动记录」最上方写清文件/函数与行为；增加有意义的回归测试。只在验收达成后勾选 ROADMAP 对应项目。
- 使用独立开发分支，完成后提交 PR，按仓库约定由其他人评审后合并。
- 测试入口必须显示 UI 是否真正运行。发布验收中需要 Playwright 的评分显示/经验结算、继续存档和 390px 手机宽度检查，缺浏览器不能被当成通过。

R1 不包含新剧情、地图美术、任务机制、角色技能重做、单人难度调整、联网、上线或付费服务接入。测量暴露的其他问题记录为后续事项；与本期测量可信度直接相关的流程/结算错误纳入 R1。

## 6. 联机边界（D，保留设计，暂不实现）

保留路线图已定要求：在线合作 2–4 人、在线跑团主持人 + 玩家；每人只控自己角色及其武器人；每个我方回合选顺序；协助询问对应玩家本人；房主权威结算并广播状态/演出；联机隐藏撤销。

开发顺序仍为 D1 统一指令 → D2 归属/顺序/热座 → D3 房间服务 → D4 主持人权限。正式动工前须确定共同决策、掉线/重连、协助超时、抢同一顺序格、倒地/永久死亡后的参与方式，以及托管成本与平台。

主持人保密数据必须在对玩家发送的状态中移除，不能只隐藏页面元素。统一指令有利于测试，但未经额外设计不能承诺任意版本都支持确定性录像回放。
